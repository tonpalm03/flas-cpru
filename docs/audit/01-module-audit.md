# รายงานตรวจระบบบริหารงานคณะก่อนใช้งานจริง

วันที่ตรวจ: 28 กันยายน 2569 ตามวันที่ของเซสชัน เอกสารนี้เป็นผลตรวจโค้ดและเอกสารในเครื่อง ณ รอบนี้ ไม่ใช่การรับรองระบบที่ deploy อยู่

**ผลประเมิน: ยังไม่พร้อมใช้เป็นระบบงานจริงร่วมกันหลายคน** มีหน้าจอครบตามเมนูหลัก แต่ข้อมูลธุรกรรมส่วนใหญ่เป็นข้อมูลตัวอย่างและ React state การอนุมัติ การจัดเก็บหลักฐาน และการเชื่อมงบประมาณยังไม่ครบ จำเป็นต้องทำระบบพื้นฐานก่อน แล้วตรวจรับทีละโมดุลตามรายละเอียดต่อไปนี้

## 1. ขอบเขตและหลักฐานการตรวจ

- ตรวจเส้นทางหน้าเว็บ 22 หน้า: เมนูย่อย 19 หน้าใน 6 โมดุล รวมหน้าหลัก `/`, เข้าสู่ระบบ `/login` และผังงาน `/flow`
- ตรวจ Sidebar, Navbar, RoleContext, types, Firebase/auth/service, generator, template config, seed และการตั้งค่า build/hosting
- ทำบัญชีเอกสารต้นทาง 156 ไฟล์: PDF 87, DOCX 39, DOC 17, XLSX 5, XLS 1, JPG 7
- สกัดข้อความ DOCX 39 และ DOC 17 ไฟล์ อ่านโครงสร้าง Excel ทั้ง 6 ไฟล์ รวมถึงสูตรและหัวตารางที่เกี่ยวข้อง สกัดข้อความ PDF ได้ 37 ไฟล์ อีก 50 ไฟล์ไม่มีข้อความเพียงพอสำหรับการตรวจอัตโนมัติ
- อ่านภาพ JPG สำคัญ 6 ไฟล์ และตรวจภาพ PDF แผนงบประมาณ 1 หน้า ระเบียบค่าสอน 4 หน้า และระเบียบค่านิเทศ 2 หน้า รวมถึงตรวจแบบฟอร์ม/เช็คลิสต์หลักจากข้อความต้นฉบับ
- การสกัดข้อความสำเร็จไม่เท่ากับตรวจละเอียดทุกหน้า ทุกยอดเงิน หรือทุกไฟล์แนบ โครงการ PDF รายฉบับที่สแกนยังต้อง OCR และทวนข้อมูลก่อนนำเข้าระบบ ดูสถานะรายไฟล์ใน `03-source-inventory.md`
- `npx tsc --noEmit --incremental false`: ผ่าน
- `npm run build`: ผ่าน สร้าง static export ได้
- `npm run lint`: เรียกแล้วพบคำถามตั้งค่า ESLint ยังไม่ได้ตรวจ lint สำเร็จแบบไม่ต้องโต้ตอบ
- ยังไม่ได้ทดสอบกดทุกเมนูในเบราว์เซอร์ ไม่ได้ทดสอบ Firebase จริงหลายบัญชี ไม่ได้ตรวจ rules ที่ deploy จริง และไม่ได้ตรวจรูปแบบไฟล์ที่ระบบ export ทุกชนิด เกณฑ์ UAT ด้านล่างเป็นสิ่งที่ต้องทำต่อ ไม่ใช่ผลทดสอบที่ผ่านแล้ว
- ไม่แก้โค้ดระบบ ไม่เขียนข้อมูล production ไม่ deploy และไม่รัน seed ในรอบตรวจนี้

ระดับงาน: **P0** ต้องแก้ก่อนใช้ข้อมูลจริง, **P1** ต้องครบก่อนเปิดโมดุลนั้น, **P2** งานเสริมหลังแกนงานพร้อม

## 4. โมดุลที่ 1 งานธุรการและสารบรรณ

### ADMIN-01 แดชบอร์ด `/admin` — P1

มีการ์ดทางเข้าและจำนวนรายการจาก `MOCK_INBOUND_DOCS`, `MOCK_OUTBOUND_DOCS`, `MOCK_ROOMS` (`app/admin/page.tsx:22`) งานที่ต้องเติมคือยอดรับวันนี้ งานรอดำเนินการ งานเลยกำหนด หนังสือรอลงนาม และผู้รับผิดชอบจากข้อมูลจริง พร้อมทางเข้าแบบตอบรับ/เช็คลิสต์/แม่แบบให้ค้นพบง่าย

รับงานเมื่อยอดทุกการ์ดเท่ากับรายการที่กดเข้าไป ณ ตัวกรองเดียวกัน มี loading/empty/error state และไม่เอาข้อมูลจำลองมาแทนเมื่ออ่านล้มเหลว

### ADMIN-02 ทะเบียนหนังสือรับ `/admin/inbound` — P1

มีเพิ่มรายการ ค้นหา กรองความเร่งด่วน ดูรายละเอียดและ export Excel แต่ `handleCreateDoc` บรรทัด 57 เพิ่มเฉพาะ state ช่องมอบหมายเป็นข้อความ ปุ่ม routing เปิดรายละเอียดเท่านั้น และข้อความดาวน์โหลดไฟล์แนบไม่มี download handler

ต้องทำ:

1. ลงรับจริงด้วยเลขรับไม่ซ้ำ แนบต้นฉบับหลายไฟล์ ตรวจเลขหนังสือ/วันที่/หน่วยงาน และแก้ข้อมูลพร้อมเหตุผลได้
2. ส่งต่อหน่วยงานหรือบุคคลจากทะเบียนผู้ใช้ มีรับทราบ รับเรื่อง ส่งกลับ ส่งต่อซ้ำ และปิดเรื่อง แสดงประวัติหลายเหตุการณ์
3. กำหนดวันครบกำหนด ชั้นความเร่งด่วน และขอบเขตการเปิดดูไฟล์ตามที่หน่วยงานต้องใช้
4. ตาราง/รายละเอียด/export แสดงทุกสถานะตรงกัน ปัจจุบันรายละเอียดเหมารวมสถานะที่ไม่ใช่ forwarded ว่าเสร็จสิ้น และ Excel ไม่แยก most_urgent
5. กำหนด export ทั้งหมดหรือเฉพาะผลกรองให้ชัด ปัจจุบัน export ใช้ `docs` ไม่ใช่ `filteredDocs`

รับงานเมื่อสองคนลงรับพร้อมกันเลขไม่ชน ผู้รับปลายทางเห็นงานจริง ดาวน์โหลดไฟล์เดิมได้หลัง refresh และย้อนตรวจผู้ส่ง/ผู้รับ/เวลา/ข้อสั่งการได้ครบ

### ADMIN-03 ทะเบียนหนังสือส่ง `/admin/outbound` — P1

มีเพิ่ม/ค้นหา/export แต่บันทึกเฉพาะ state และสร้างแล้วเป็น `signed` (`handleCreateDoc:39`) ยังไม่มีหลักฐานการลงนามหรือจัดส่ง เลขที่สร้างจากจำนวนแถวและ form ไม่จัดเลขใหม่หลังบันทึก

ต้องเชื่อมกับร่างเอกสารและผู้ลงนาม รองรับส่งตรวจ ส่งกลับ แนบฉบับลงนาม ออกเลขอย่างปลอดภัย วันส่ง ช่องทางส่ง หลักฐานการส่ง ผู้รับหลายราย และยกเลิกเลขโดยเก็บเหตุผล

รับงานเมื่อบันทึกร่างไม่ถูกนับว่าส่งแล้ว ผู้ไม่มีสิทธิลงนามทำไม่ได้ และเอกสารที่ส่งจริงย้อนเปิดฉบับที่ใช้ส่งได้

### ADMIN-04 สร้างบันทึกข้อความ `/admin/memo-generator` — P1

มีแม่แบบ 3 แบบ: เชิญวิทยากรภายใน ขอเวลาเรียน และขอไปราชการ แก้ข้อความ/preview/export Word/เปิดหน้าพิมพ์ได้ แต่ไม่มี save draft, version, แนบเอกสาร, ลงนาม หรือเชื่อมทะเบียนส่ง

เอกสารในโฟลเดอร์มีแบบเชิญวิทยากรหลายคน แจ้งนักศึกษา หนังสือภายนอกเชิญวิทยากร/สถานที่ และบันทึกเสนออธิการบดีลงนามซึ่งยังไม่มีแม่แบบเฉพาะ ต้องทำ mapping ฟิลด์และรูปแบบแยก ไม่แทนทุกชนิดด้วยบันทึกข้อความทั่วไป

`lib/documentGenerator.ts:21` สร้างเอกสารใหม่แบบพื้นฐาน ไม่ได้เติมข้อมูลลงแบบเดิม ส่วน PDF ใช้ `window.print()` เท่านั้น ต้องมีพื้นที่พิมพ์เอกสารที่แยกจากฟอร์ม ปุ่ม และ modal และตรวจ A4 ภาษาไทย/ตราครุฑ/ลายเซ็น/การตัดหน้าในไฟล์จริง

รับงานเมื่อแก้แม่แบบส่วนกลางแล้วเอกสารใหม่ใช้ค่าที่เปลี่ยน ร่างเปิดต่อได้ ฉบับที่ลงนามไม่เปลี่ยนตามค่าปัจจุบัน และเอกสาร Word/PDF ตรงต้นฉบับที่หน่วยงานเลือก

### ADMIN-05 แบบตอบรับ `/admin/responses` — P1

## 6. โมดุลที่ 3 การเงินและงบประมาณ

### FIN-01 ทะเบียนคุมงบ `/finance` — P0/P1

มีตารางรวม allocated/committed/disbursed/remaining จาก mock และ export ค่าเป็นตาราง แต่ไม่มีรายการเคลื่อนไหว นำเข้า โอนงบ ผูกพัน ตัดจ่าย ยกเลิก และปิดปี `remainingAmount` ถูกเก็บเป็นอีกค่าหนึ่งโดยไม่มีกลไกบังคับกระทบยอด

ไฟล์ `3.คุมรายการเงินงบรายได้ 2568.xlsx` มี 27 ชีต โครงสร้างหน้ารวม → 9 โครงการ → กิจกรรม → รายการเคลื่อนไหว หัวหน้าหลัก A1 ระบุ 2569 ทั้งที่ชื่อไฟล์เป็น 2568 และบางหัวกิจกรรมยังระบุเดือนปีเดิม ต้องยืนยันปีจากเนื้อหาและเจ้าของข้อมูล ไม่อนุมานจากชื่อไฟล์

ต้องทำ ledger แยกปี/แหล่งเงิน/โครงการ/กิจกรรม/หมวด/รายการ/เอกสารอ้างอิง กำหนดความหมาย “ขออนุมัติ”, “ผูกพัน”, “ใช้จ่าย”, “เบิกจ่ายจริง” ให้ชัด เพื่อไม่หักเงินซ้ำเมื่อเงินยืมส่งใช้หรือ PR เปลี่ยนเป็นการเบิกจ่าย ตรวจวงเงินที่ฝั่ง trusted operation และป้องกันส่งซ้ำ

ต้องมีนำเข้าแบบ preview+mapping+validation+duplicate check+reconciliation และ audit ยอดตั้งต้น ไม่ import ทุกเซลล์โดยตรง มีรายงานรายไตรมาส แยกเงินรายได้/แผ่นดิน ปฏิทินปิดรับเอกสาร และรายการกันเงิน/ข้ามปีตาม policy ที่หน่วยงานรับรอง

รับงานเมื่ออนุมัติรายการพร้อมกันไม่ทำให้เกินงบ การยกเลิกมี reversing entry ยอดโครงการเท่ากับกิจกรรมและรายการประกอบ และ import ซ้ำไม่เพิ่มยอดซ้ำ

เพิ่มวันที่กิจกรรม วันที่รับเอกสาร วันที่จ่ายเงิน ฐานคำนวณกำหนดคืนตามชนิดงาน ปฏิทินวันทำการ การยื่นล่วงหน้า ข้อยกเว้นพร้อมผู้อนุมัติ สถานะเลยกำหนด ยอดส่งใช้และยอดค้าง เชื่อมเอกสารโครงการและ ledger โดยไม่ลงค่าใช้จ่ายซ้ำ

รับงานเมื่อยังไม่จ่ายเงินไม่ถูกนับว่าผู้ยืมได้รับเงิน ส่งใช้บางส่วนแล้วคงเหลือถูกต้อง แนบหลักฐานไม่ครบยังส่งต่อไม่ได้ และพิมพ์ได้สัญญาเต็มแทนสรุป modal

### FIN-03 เบิกค่าสอน/ค่านิเทศ `/finance/disbursement` — P0/P1

มีตารางชั่วโมง×อัตรา หัก 1% เพิ่ม/ลบแถว export Excel และ memo แต่ไม่มีฐานข้อมูลและ workflow “ค่านิเทศ” ในเมนูยังไม่มีแบบคำนวณรายนักศึกษา/ครั้งต่างหาก

ข้อผิดพลาดเฉพาะ: แถวใหม่ใช้ `id: items.length + 1` หากลบแถวกลางแล้วเพิ่มอาจซ้ำกับ ID เดิม และ `handleRemoveItem` ลบทุกแถวที่ ID เดียวกัน ต้องใช้ ID ที่ไม่ขึ้นกับจำนวนแถว จำนวนอาจารย์ใน memo ใช้ `items.length` จึงนับซ้ำเมื่อคนเดียวสอนหลายวิชา

เอกสารค่าสอนต้นทางมีสัปดาห์ วันที่ จำนวนผู้เรียน ห้องเรียน เวลาเริ่ม/จบ รายวิชา ชั่วโมง อัตรา และลายเซ็น ซึ่งหน้าจอยังขาด ระเบียบ PDF ในโปรเจกต์มีเงื่อนไขระดับการศึกษา จำนวนนักศึกษา ภาระงาน และการส่งผลการเรียน ระบบปัจจุบันเปิดให้กรอกอัตราเองโดยไม่ตรวจเงื่อนไข

ต้องแยก:

- ค่าสอน: เทอม/ปีการศึกษา/หลักสูตร/รายวิชา/กลุ่มเรียน/อาจารย์/ครั้งที่สอน/จำนวนนักศึกษา/เวลาสอน/ชั่วโมง/อัตราตามรุ่น policy/ผู้ตรวจ พร้อมป้องกันเบิกซ้ำ
- ค่านิเทศ: นักศึกษา สถานที่ฝึก ผู้รับผิดชอบ ครั้งที่นิเทศ วิธีนิเทศ วันเดินทาง หลักฐานการนิเทศและเพดานตาม policy ไม่คำนวณจากชั่วโมงสอน
- ค่าตอบแทนบัณฑิตศึกษา เช่น สอบ/ที่ปรึกษา/ตรวจรูปแบบ เป็นงานต่อยอดที่พบในเอกสารและควรยืนยันว่ารวมในรอบเปิดใช้งานหรือไม่
- ภาษีและ VAT ต้องกำหนดตามประเภทรายการและผู้รับเงินโดยเจ้าของ policy พร้อมวันมีผล ห้ามถือค่า hardcode 1%/7% ว่าใช้ได้ทุกกรณี

รับงานเมื่ออัตราแสดงที่มาจาก policy คำนวณและปัดเศษตามกติกาที่ตกลง ป้องกันรายการซ้ำ ใช้จำนวนบุคคลไม่ซ้ำอย่างถูกต้อง มีการตรวจ อนุมัติ จ่ายเงินจริงและหลักฐาน จึงเปลี่ยน paid

### FIN-04 ระบบการเงินที่เอกสารมีแต่ยังไม่มีเมนูเฉพาะ — P1

1. อนุมัติจ่ายเงินโครงการทั่วไป: ค่าตอบแทนวิทยากร อาหาร อาหารว่าง สถานที่ และค่าใช้จ่ายอื่น พร้อมชุดเอกสารตามประเภท
2. ส่งใช้เงินยืม: รองรับใบสำคัญหลายใบ/เงินสดหลายครั้ง กระทบยอดและปิดหนี้
3. เดินทางไปราชการ: คำขอ รายชื่อ วันเวลา สถานที่ เส้นทาง ค่าใช้จ่าย แบบ 8708 และ บก.4231 ตาม checklist ต้นทาง
4. ใบสำคัญรับเงิน: ผู้รับ/ผู้จ่าย รายการ หน่วย จำนวนเงินตัวเลข/ตัวอักษร ลายมือชื่อ และไฟล์ประกอบที่จำกัดสิทธิ
5. การตรวจตัดแผนก่อนเบิก: คิวผู้ตรวจวงเงิน เหตุผลส่งกลับ และหลักฐานรายกิจกรรมเชื่อมกับโครงการ

## 7. โมดุลที่ 4 พัสดุและจัดซื้อ `/procurement`

### PROC-01 คำขอซื้อ/จ้าง — P1

มีฟอร์มและรายการวัสดุ เพิ่ม/ลบรายการ คิด VAT 7% และ export Excel แต่ `reqs` ไม่ถูกเพิ่ม/บันทึกจริง เป็นเพียงแหล่งจำนวนรายการเพื่อสร้างเลขเริ่มต้น ไม่มีส่งตรวจหรือทะเบียนวงจรจัดซื้อ

`exportPurchaseRequisitionExcel` รับ projectName/requesterName/department/requestDate แต่ไม่ได้เขียนข้อมูลเหล่านี้ลงชีต ส่งออกเฉพาะรายการและยอด และ budgetSource ไม่ได้ส่งเข้า generator ค่า VAT จากหน้าจัดการแม่แบบก็ไม่ถูกใช้

ต้นทาง `ใบขอซื้อ-ขอจ้างซื้อ.doc` และ `แบบกรอกการขอซื้อ-ขอจ้าง.xlsx` ต้องมีประเภทซื้อ/จ้าง วัสดุ/ครุภัณฑ์ โครงการ/กิจกรรม แหล่งงบ วันต้องการใช้ รายชื่อกรรมการตรวจรับ TOR/Spec ใบเสนอราคา และรายการเอกสารผู้ขาย รวมถึงความเห็นผู้ตรวจงบและผู้อนุมัติ

ต้องทำทะเบียน PR พร้อม line IDs, ผู้ขาย/ผู้รับจ้าง, เอกสารแนบ, ตรวจเอกสารตามเงื่อนไข, workflow ขอซื้อ→ตรวจงบ→อนุมัติ→ดำเนินการจัดซื้อ→ส่งมอบ→ตรวจรับ→ส่งเบิก; รองรับส่งกลับ/ยกเลิก/ส่งมอบบางส่วนตามขอบเขตที่ตกลง มีผูกพันงบและคืนวงเงินที่ไม่ซ้ำ

แบบฟอร์ม Excel ระบุให้เสนอเรื่องก่อนวันรับพัสดุ 10 วันทำการ จึงต้องมีปฏิทินวันทำการและข้อยกเว้นพร้อมผู้อนุมัติตาม policy ที่หน่วยงานยืนยัน

รับงานเมื่อ save/reopen ได้คำขอเดิม export มีหัวเอกสารและผู้ลงนามครบ อัตราภาษีในหน้าและไฟล์ตรงกัน รายการไม่เกินวงเงิน สถานะ inspected เกิดจากการตรวจรับจริง และมีประวัติผู้ทำทุกขั้น

ทะเบียนครุภัณฑ์/สต็อกวัสดุ/เบิกคืน/ซ่อมบำรุงเป็นระบบต่อยอดที่อาจต้องมีหากคาดหวังโมดุลพัสดุครบวงจร แต่เอกสารที่พบรองรับความต้องการซื้อ/จ้างเป็นหลัก จึงไม่ถือว่าระบบสต็อกทั้งหมดได้รับการยืนยันขอบเขตแล้ว

## 8. โมดุลที่ 5 บุคลากร

### HR-01 การลา `/hr` — P0/P1

มีฟอร์มลา 3 ชนิด ตาราง และพิมพ์ แต่บันทึกเป็น approved ทันทีและตารางแสดงอนุมัติทุกแถว จำนวนวันเป็นค่ากรอกแยกจากวันที่ สิทธิคงเหลือเป็นข้อความคงที่ ไม่มีฐานข้อมูลยอดสะสม/ใช้จริง/วันหยุด/แนบใบรับรองแพทย์

แบบ PDF ต้นทางมีวันสะสม สิทธิปีปัจจุบัน ผู้รับมอบหมายงาน สถิติการลา ผู้ตรวจสอบ และความเห็นผู้บังคับบัญชาหลายขั้น จึงต้องมี employee ID, ประเภทบุคลากร, policy สิทธิลา, ปฏิทินวันทำการ, คำนวณวัน/ครึ่งวันถ้าหน่วยงานใช้, ตรวจลาซ้อน, ยอดรออนุมัติ/ใช้จริง, ผู้แทนรับทราบ, ส่งตรวจ อนุมัติ ปฏิเสธ ยกเลิก และแนบหลักฐาน

ต้องออกใบลาพักผ่อนและใบลาป่วย/ลากิจตามต้นฉบับแยกกัน การพิมพ์ตารางประวัติไม่ใช่เอกสารใบลาเฉพาะรายการ

รับงานเมื่อช่วงวันหยุดไม่ถูกนับเป็นวันทำการตามปฏิทินที่ใช้ การยื่นลาไม่อนุมัติตัวเอง ผู้ใช้เห็นข้อมูลตามสิทธิ ยกเลิกหลังอนุมัติคืนวันลาถูกต้อง และข้อมูลสำคัญตรงแบบฟอร์ม

### HR-02 ประวัติและผลงาน `/hr/portfolio` — P1

มีฟอร์มประวัติอย่างย่อ/ภาระสอน/วิจัย/บริการวิชาการ และ export memo แต่ไม่มีหลายบุคลากร ไม่มีประวัติหลายรายการ ไม่มีอัปโหลดหลักฐาน และไม่มีปีประเมินหรือ workflow รับรอง

ต้องแยกทะเบียนบุคลากร วุฒิการศึกษา ตำแหน่ง ภาระงานสอน วิจัย ผลงาน บริการวิชาการ และหลักฐานต่อรายการ พร้อม SAR ตามรอบ ประวัติ version และสิทธิแก้/อ่านระดับบุคคล

ไฟล์ `ประวัติและผลงาน_ฤทธิชัย_V5-2.doc` เป็นข้อมูลจริงเฉพาะบุคคล ต้องทำ mapping โครงสร้างและยืนยันความถูกต้องก่อนนำเข้า ไม่ใช้ข้อมูลตัวอย่างใน UI เป็นประวัติจริงของผู้ login

### HR-03 สัญญาจ้างที่ขาด — P1 หากอยู่ในขอบเขตเปิดใช้ HR

พบ `สัญญาปฏิบัติงานของพนักงานจ้างตามภารกิจ-ประเภทวิชาการ1.pdf` แต่ในระบบมีเพียงข้อความ contractType ใน portfolio ไม่มีเลขสัญญา ระยะเวลา วันเริ่ม/สิ้นสุด ผู้ลงนาม ค่าตอบแทน ไฟล์สัญญา หรือการต่อสัญญา

เพิ่มทะเบียนสัญญาจ้างและเอกสารลงนาม การแจ้งเตือนก่อนครบกำหนด ประวัติต่อสัญญา/เปลี่ยนแปลง และจำกัดข้อมูลส่วนตัว/ค่าตอบแทนตามผู้มีสิทธิ หากมหาวิทยาลัยมีระบบ HR กลางอยู่แล้ว ให้กำหนดว่าจะเชื่อม/อ้างอิงหรือจัดเก็บในคณะก่อนพัฒนา

รับงานเมื่อบุคลากรสองคนเห็นเฉพาะข้อมูลที่อนุญาต ประวัติเก่ายังอยู่ และไม่ปิด/ต่อสัญญาอัตโนมัติโดยไม่มีผู้รับผิดชอบ

## 9. โมดุลที่ 6 แผนและตัวชี้วัด `/plan`

### PLAN-01 แผน/KPI — P1

ปัจจุบันเป็นการ์ด 4 ยุทธศาสตร์พร้อมตัวเลขคงที่ ไม่มีหน้าบันทึก ไม่มีฐานข้อมูล และข้อความ “ระบบเชื่อมต่อ 100%” ไม่สอดคล้องกับการเชื่อมต่อที่ตรวจพบ ความก้าวหน้า 86.7% ก็ไม่ได้คำนวณจาก records

ต้องทำทะเบียนแผนรุ่น/ปี พันธกิจ ยุทธศาสตร์ เป้าประสงค์ OKR/KPI หน่วยนับ สูตรเป้าหมาย/ผลจริง น้ำหนัก รอบรายงาน ผู้รับผิดชอบ ผู้รับรอง และหลักฐาน ผูก project/activity แบบหลายต่อหลายเพื่อไม่บวกผลซ้ำ

เพิ่มการเลือกปี ไตรมาส ประเภทโครงการ สาขา สถานะส่งรายงาน กราฟ/รายงานที่ย้อนดูรายการประกอบได้ ค่าความก้าวหน้าต้องคำนวณตามสูตรและน้ำหนักที่หน่วยงานยืนยัน แยก KPI ไม่มีข้อมูลจากค่า 0 และป้องกันหารศูนย์

เอกสาร `แผนปฏิบัติราชการ 2569.pdf` ในโฟลเดอร์มีเพียง 1 หน้า เป็นหน้าตารางงบประมาณพิมพ์เลขหน้า 26 ไม่ใช่แผนยุทธศาสตร์ทั้งเล่ม จึงยังขาดเอกสารแผนฉบับเต็ม/ตาราง KPI ที่รับรองสำหรับตั้ง master plan ห้ามสร้างค่าจริงจาก 4 การ์ดตัวอย่าง

รับงานเมื่อเพิ่มผลของโครงการที่อนุมัติแล้ว KPI ที่เกี่ยวข้องเปลี่ยนตามสูตร กดดูที่มาได้ รายงานขาดหลักฐานไม่ถูกนับว่าผ่าน และย้อนดูแผนปีก่อนได้โดยไม่ใช้เป้าหมายปีปัจจุบัน

## 11. เอกสารและข้อมูลที่ยังต้องจัดหา/ยืนยัน

รายการนี้แยกจาก “ระบบที่ยังขาด”: บางเรื่องพัฒนาโครงสร้างรอได้ แต่ห้ามเปิดใช้กติกาที่เดาเอง

1. แผนยุทธศาสตร์/แผนปฏิบัติราชการฉบับเต็ม ตารางเป้าหมาย KPI และคำจำกัดความที่รับรอง
2. บัญชีผู้มีอำนาจอนุมัติ/รักษาการ/ปฏิบัติราชการแทน แยกชนิดงานและวันเริ่ม–สิ้นสุด รวมถึงรหัสหนังสือหน่วยงานที่ถูกต้อง เอกสารและ seed/UI ใช้ชื่อ/รหัสต่างกัน
3. สรุป policy ล่าสุดที่หน่วยงานยืนยัน: อัตราค่าสอน/นิเทศ เงื่อนไขภาษี สิทธิลา กำหนดส่งใช้เงินยืม ปฏิทินวันทำการ และข้อยกเว้น
4. แม่แบบเอกสารฉบับมาตรฐานที่เลือกใช้จริง โดยเฉพาะเอกสารที่ชื่อเหมือนกันแต่คนละรุ่น/มีลายเซ็นอยู่แล้ว
5. ข้อมูล master ผู้ใช้ บุคลากร สาขา ห้อง รถ คนขับ ผู้ขาย ผู้รับเงิน และโครงการที่ผ่านอนุมัติ พร้อมผู้รับผิดชอบการตรวจข้อมูล
6. ปีที่ถูกต้องของสมุดคุมงบชื่อ 2568/หัวรายงาน 2569 และยอดตั้งต้น/ยอดยกมา ณ วันเริ่มใช้ระบบ
7. ขอบเขตเชื่อมระบบมหาวิทยาลัยกลาง และวิธีรับส่งเอกสารเมื่อผู้อนุมัติอยู่นอกคณะ เช่น อธิการบดี/กองคลัง/กองนโยบายและแผน
8. ผู้ดูแล production ขั้นตอนสำรองและกู้คืน ระยะเวลาเก็บเอกสาร และคู่มือการเปิดปี/ปิดปี

## 12. ลำดับพัฒนาและเงื่อนไขผ่านก่อนย้ายโมดุล

1. CORE: auth/permissions/rules/schema/master/ไฟล์/audit/เลขทะเบียน ทำให้ข้อมูลปลอดภัยและบันทึกจริงก่อน
2. ธุรการ: เดินครบรับ→ส่งต่อ→ร่าง→ตรวจ→ลงนาม→ส่ง พร้อม checklist/แม่แบบ/คำสั่ง/จอง
3. โครงการ: ข้อเสนอครบต้นแบบ→ส่งตรวจ→อนุมัติ→กิจกรรม→รายงานและ SDG ใช้ ID เชื่อมงานทั้งหมด
4. การเงินแกนกลาง: ledger/วงเงิน/ผูกพัน/จ่าย/ส่งใช้ พร้อมกระทบยอด และค่าสอน/นิเทศแยกประเภท
5. พัสดุ: ขอซื้อ→ตรวจงบ→ดำเนินการ→ตรวจรับ→ส่งเบิก เชื่อม ledger และคำสั่งกรรมการ
6. บุคลากร: employee/leave policy/ลา/portfolio/สัญญาจ้าง ตามขอบเขตที่ตกลง
7. แผนและ dashboard: สร้างค่าจริงจากโครงการ/การเงิน/ผล KPI ที่รับรองแล้ว
8. UAT รวมและเปิดใช้: ทดลองหลายบทบาท หลายเครื่อง ปิดปี/restore และเอกสารจริง

ทุกโมดุลต้องผ่าน: save แล้ว refresh/เปิดอีกเครื่องข้อมูลอยู่, ข้อมูลไม่รั่วข้ามสิทธิ, สถานะเปลี่ยนได้เฉพาะผู้มีสิทธิ, แนบ/ดาวน์โหลดได้จริง, เงิน/วัน/จำนวนตรวจขอบเขต, error ไม่กลายเป็นสำเร็จ, export ตรงข้อมูลและต้นแบบ, มี audit trail, ผู้ใช้งานฝ่ายนั้นทวนผล

ยังไม่ควรใช้เปอร์เซ็นต์ “พร้อม 100%” จากจำนวนหน้า/การ build ผ่านเป็นตัวชี้วัดความสำเร็จ ให้ใช้เส้นทางงานที่ผ่านเกณฑ์ตรวจรับเป็นรายโมดุล

## 13. สถานการณ์ทดสอบรวมสำหรับส่งมอบ

|---|---|---|
| UAT-01 | บุคคลไม่ login เรียกอ่าน/เขียนข้อมูลและไฟล์โดยตรง | ถูกปฏิเสธตาม policy ทั้ง UI และ data layer |

| UAT-05 | หนังสือรับ→มอบหมาย→ผู้รับรับทราบ→ร่างตอบ→ลงนาม→ส่ง | ตรวจผู้รับผิดชอบและหลักฐานย้อนหลังได้ |
