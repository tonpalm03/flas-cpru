## ขอบเขตและผลรวม

แก้ชื่อหัวข้อโมดุลแล้วตามลำดับ: **งานธุรการ / งานโครงการ / การเงิน / พัสดุ / บุคคล / ตั้งค่าระบบและผู้ใช้งาน / งานแผน** ใน sidebar รวมทั้งชื่อการ์ดและหัวหน้าหลักที่มีอยู่ การเปลี่ยนครั้งนี้ไม่ได้เปลี่ยนชื่อหน่วยงานในข้อมูลทะเบียน และไม่ได้แก้กระบวนการธุรการตามข้อค้นพบด้านล่าง

ระบบพัฒนาจากรายงานกันยายนแล้ว: มี service อ่าน/เขียน Firestore, อัปโหลดไฟล์, บันทึกร่าง, ประวัติรายการ และ counter transaction หลายส่วน จึงไม่ควรใช้ข้อสรุปเดิมว่าเมนูทั้งหมดมีแต่ state/mock อย่างไรก็ตาม **ยังไม่ควรเปิดใช้กับข้อมูลจริงหลายบัญชีจนกว่าข้อ P0 และ P1 ที่เกี่ยวข้องจะผ่านการตรวจรับ**

P0 = ต้องแก้ก่อนใช้ข้อมูลจริง; P1 = กระบวนการหลักไม่ครบหรือข้อมูลสูญหาย; P2 = ความสะดวก/ความชัดเจนที่ควรปรับหลังส่วนหลักทำงานได้

## 0. ฐานระบบที่ต้องแก้ร่วมก่อนเริ่มรับหนังสือจริง

ข้อกำหนดบทบาทเพิ่มเติมจากผู้ใช้: อ่าน [บทบาทผู้ใช้และสิทธิ์จัดการบัญชี](<D:/Faculty of Liberal Arts and Sciences/docs/specs/roles-user-management.md>) ก่อนออกแบบสิทธิ์ ยืนยันครบ 7 บทบาท: แอดมิน คณบดี รองคณบดี ผู้บริหาร ประธานสาขา อาจารย์ เจ้าหน้าที่ โดยแอดมินแต่งตั้งบทบาท แก้ไขรหัสผ่าน และลบบัญชีได้

### ADM-00A — P0: บังคับสิทธิ์ที่ฐานข้อมูล

หลักฐาน: [firestore.rules](<D:/Faculty of Liberal Arts and Sciences/firestore.rules:36>) โดยเฉพาะ `users`, `admin_documents_in`, `admin_documents_out`, `memos`, `rooms`, `orders`, `admin_responses`, `system_counters`

- rules ให้ผู้ login ทุกคนสร้าง/แก้ทะเบียนธุรการส่วนใหญ่ได้ โดยไม่ตรวจผู้รับผิดชอบ บทบาท สถานะบัญชี หรือการเปลี่ยนสถานะเอกสาร; `rooms` ลบได้ด้วย
- การสร้าง `users/{uid}` ตรวจเพียง uid ตรงกัน ไม่บังคับ role/status เริ่มต้น จึงมีช่องทางสร้างโปรไฟล์ตนเองเป็น admin ในกรณียังไม่มีโปรไฟล์ แม้หน้าเว็บไม่ได้เปิดปุ่มให้ทำ
- `isAdmin()` มีทางผ่านด้วยอีเมลที่เขียนตายตัว ไม่ได้อิงเฉพาะสิทธิ์ที่ผู้ดูแลจัดสรร
- counter เปิดให้ผู้ login เขียนโดยตรง จึงแก้เลขย้อนหลังได้; audit create ไม่ตรวจว่า actor ตรงกับผู้ login

งานส่งต่อ: กำหนดตารางสิทธิ์อ่าน/สร้าง/แก้/ส่งต่อ/ตรวจ/ลงนาม/ยกเลิก แยกเจ้าของเรื่อง เจ้าหน้าที่ธุรการ ผู้อนุมัติ ผู้ดูแล ตรวจบัญชี active และ whitelist ฟิลด์ ห้าม client ยกระดับ role หรือเปลี่ยนผลอนุมัติเอง ใช้ trusted backend สำหรับงานที่ต้องตรวจหลายเงื่อนไข หรือ rules/transaction ที่พิสูจน์ได้ว่าเพียงพอ

ตรวจรับ: ทดสอบด้วย Emulator อย่างน้อยผู้ใช้ทั่วไป เจ้าหน้าที่ธุรการ ผู้อนุมัติ admin และบัญชีปิดใช้งาน โดยเรียก SDK โดยตรงด้วย ไม่ใช่ดูเฉพาะปุ่ม ต้องปฏิเสธการสร้าง admin เอง การแก้เอกสารคนอื่นที่ไม่มีสิทธิ์ การข้ามสถานะ และการลดเลข counter

### ADM-00B — P0: แยกข้อมูลจริงกับข้อมูลทดลอง และรับมือความผิดพลาด

หลักฐาน: [firebaseService.ts](<D:/Faculty of Liberal Arts and Sciences/lib/firebaseService.ts:156>) และ [firebase.ts](<D:/Faculty of Liberal Arts and Sciences/lib/firebase.ts>)

- getters หลายตัวคืน local/mock ทั้งเมื่อ cloud ว่างและเมื่ออ่านผิดพลาด ทำให้ผู้ใช้แยกไม่ออกว่าไม่มีรายการ อ่านไม่ได้ หรือเป็นข้อมูลจำลอง
- writes ที่ตรวจหลายตัวโยน error แล้ว ซึ่งดีขึ้นจากเดิม แต่ไม่ได้แก้ปัญหาฝั่ง read
- payload ใช้ spread ข้อมูลที่มี `undefined` เช่นหนังสือรับไม่แนบไฟล์ แบบตอบรับไม่มีกลุ่มผู้เข้าร่วม และการจองห้องที่ไม่มีข้อมูลรถ ขณะที่ `firebase.ts` ใช้ `getFirestore` ไม่ได้ตั้งให้ข้าม undefined เส้นทางเหล่านี้จึงมีข้อมูลที่ Firestore ไม่ยอมรับ ต้องทดสอบและแก้ทุก payload ที่เกี่ยวข้อง
- `uploadDocumentFile` ในโหมด local คืน object URL ซึ่งใช้เป็นไฟล์ถาวรข้ามการปิดหน้า/เครื่องไม่ได้

งานส่งต่อ: production ต้องคืน `[]` เมื่อว่าง และแสดง error/retry เมื่ออ่านไม่ได้; demo ต้องเปิดอย่างชัดเจนและไม่ปะปน production ตรวจ schema และตัด optional undefined ก่อนส่ง หรือใช้ null ตามความหมายที่กำหนด ไม่ใช้ fallback ซ่อนความผิดพลาด

ตรวจรับ: ฐานว่างต้องไม่แสดงตัวอย่าง; ปิดสิทธิ์อ่านต้องเห็น error; สร้างรายการที่ไม่แนบไฟล์/ไม่มี optional fields ต้องสำเร็จ; reload และเปิดอีกบัญชีต้องเห็นข้อมูลที่ควรเห็นตรงกัน

### ADM-00C — P0: เลขทะเบียนและปี

หลักฐาน: [numberingService.ts](<D:/Faculty of Liberal Arts and Sciences/lib/numberingService.ts:27>), [createInboundDoc](<D:/Faculty of Liberal Arts and Sciences/lib/firebaseService.ts:170>), [orders](<D:/Faculty of Liberal Arts and Sciences/app/admin/orders/page.tsx:159>)

- counter มี transaction แล้ว แต่เมื่อ transaction ล้มเหลวยังแจกเลขจาก localStorage ซึ่งไม่ประสานกันระหว่างเครื่อง
- จองเลขกับบันทึกเอกสารแยกกัน; save ล้มเหลวอาจกินเลข และ retry อาจสร้างรายการซ้ำ
- เลขรับส่งปี 2569 ตายตัว; คำสั่งใช้จำนวนรายการบนหน้าจอ; เลขหนังสือส่งที่แสดงไม่ได้ใส่ปีแม้ counter แยกปี ต้องกำหนดความเป็นเอกลักษณ์ด้วยชนิดทะเบียน/หน่วยงาน/ปี/เลข

งานส่งต่อ: เลือกปีทะเบียนตามนโยบายหน่วยงานอย่างชัดเจน ไม่เหมารวมว่าทุกทะเบียนใช้ปีงบประมาณ; ตั้ง counter/record หรือ reservation ที่ตรวจสอบได้ภายในธุรกรรมเดียว มี idempotency key, unique key และประวัติยกเลิก/เลขเว้น ห้ามแจกเลขท้องถิ่นแทนเมื่อ production ผิดพลาด

ตรวจรับ: ผู้ใช้สองคนสร้างพร้อมกันเลขไม่ซ้ำ, กดซ้ำ/retry ไม่เพิ่มเอกสาร, transaction fail ไม่ออกเลขปลอม, เปลี่ยนปีทำงานได้โดยไม่แก้ source และเปิดเอกสารเก่าได้ตามปีเดิม

### ADM-00D — P0/P1: ไฟล์แนบและหลักฐานการเปลี่ยนแปลง

หลักฐาน: [uploadDocumentFile](<D:/Faculty of Liberal Arts and Sciences/lib/firebaseService.ts:1582>), [auditService.ts](<D:/Faculty of Liberal Arts and Sciences/lib/auditService.ts>), [firebase.json](<D:/Faculty of Liberal Arts and Sciences/firebase.json>)

- ไม่พบ Storage rules ที่อ้างผ่าน firebase.json ใน repo จึงยังยืนยันสิทธิ์ของ Storage ที่ deploy จริงไม่ได้ ไม่ใช่หลักฐานว่า bucket เปิดสาธารณะ
- upload service ไม่มีการบังคับชนิด/ขนาดไฟล์เอง ใช้ download URL เป็นหลัก
- audit เชื่อ actor ที่ client ส่งมา; เขียน audit พลาดแล้วถอยไป local buffer 100 รายการโดยไม่ทำให้ธุรกรรมหลักล้มเหลว จึงยังไม่ใช่ประวัติส่วนกลางที่ครบและน่าเชื่อถือ

งานส่งต่อ: เพิ่ม Storage rules และทดสอบชนิด/ขนาด/ผู้มีสิทธิ์ จัดเก็บ storagePath, originalName, mimeType, size, uploadedBy, เวลา และ version ตามที่จำเป็น จัดการไฟล์กำพร้าจาก upload สำเร็จแต่บันทึกเอกสารล้มเหลว ผูก actor กับ Auth และเก็บ audit ของงานสำคัญอย่างเชื่อถือได้

ตรวจรับ: คนไม่มีสิทธิ์อ่าน/อัปโหลดไม่ได้, ไฟล์ยังเปิดได้หลัง reload ตามสิทธิ์ที่กำหนด, ไฟล์เกินกำหนดถูกปฏิเสธ, แก้/ส่งต่อ/ยกเลิกมีผู้กระทำ เวลา เหตุผล และค่าเดิม/ใหม่ที่จำเป็น ห้ามปลอม actor

## 1. แดชบอร์ดงานธุรการ — /admin

หลักฐาน: [หน้าแดชบอร์ด](<D:/Faculty of Liberal Arts and Sciences/app/admin/page.tsx>), [Sidebar](<D:/Faculty of Liberal Arts and Sciences/components/Sidebar.tsx:59>)

มีแล้ว: โหลดทะเบียนรับ/ส่ง จองห้อง คำสั่ง และบันทึกข้อความมาสรุป พร้อมทางเข้าหน้าย่อย

P1/P2 ที่เหลือ:

- ยอดอาจนับข้อมูล fallback; badge “4 ใหม่” บน sidebar เป็นค่าคงที่
- โหลดครั้งเดียวเมื่อเปิดหน้า ไม่ได้รับการเปลี่ยนแปลงจากผู้ใช้อื่นทันที
- วันที่วันนี้ใช้ `toISOString().split("T")[0]` ซึ่งเป็น UTC; ช่วงก่อน 07:00 น. ไทยอาจนับการจองคนละวัน
- ควรมีงานที่ฉันต้องทำ งานใกล้ครบกำหนด/เกินกำหนด และระบุเวลาปรับปรุงข้อมูล แทนให้ดูยอดรวมอย่างเดียว

Flow ที่เสนอ: เปิดหน้า → ตรวจสิทธิ์ → โหลดสรุปตามสิทธิ์ → คลิกยอด → ไปทะเบียนพร้อมตัวกรองเดียวกัน → ทำงาน → ยอดอัปเดต

ตรวจรับ: ยอดกับรายการกรองตรงกัน, ฐานว่างเป็นศูนย์, อ่านพลาดไม่แสดงศูนย์หลอก, badge อิงรายการจริง, ทดสอบวันไทยข้ามเที่ยงคืน

## 2. ทะเบียนหนังสือรับ — /admin/inbound

หลักฐาน: [หน้า inbound](<D:/Faculty of Liberal Arts and Sciences/app/admin/inbound/page.tsx:67>), [service สร้าง/เปลี่ยนสถานะ](<D:/Faculty of Liberal Arts and Sciences/lib/firebaseService.ts:170>)

มีแล้ว: สร้างทะเบียน อัปโหลดไฟล์ กรองความเร่งด่วน/สถานะ/ฝ่าย ส่งออกตามรายการกรอง แทงเรื่องและปิดเรื่อง

ข้อบกพร่อง P1:

1. `routingPerson` มีช่องกรอก แต่ปุ่มยืนยันส่งเพียง id/status/actionNote/dept ไป `handleUpdateStatus` จึงไม่บันทึกผู้รับแทงเรื่องที่เลือกใหม่
2. ฝ่ายรับผิดชอบเริ่มต้นเป็นฝ่ายการเงิน ทำให้รายการใหม่มีแนวโน้มเข้า `forwarded` ทันทีโดยยังไม่ได้ตัดสินใจส่งเรื่อง
3. update เปลี่ยนค่าปัจจุบัน ไม่ได้สร้างลำดับผู้รับ-ส่งเรื่องที่ครบสำหรับติดตามงาน; ยังขาดขั้นผู้รับรับทราบ/ตีกลับ พร้อมกำหนดส่งและเหตุผลปิด
4. ข้อ P0 เรื่องสิทธิ์ ปีเลขรับ และ optional file กระทบหน้านี้โดยตรง

Flow ที่เสนอ: รับหนังสือ/ตรวจซ้ำ → ลงทะเบียน → ผู้มีสิทธิ์สั่งการ → เลือกหน่วยงานและผู้รับผิดชอบจากบัญชีจริง → ผู้รับรับทราบ → ดำเนินการ/ส่งต่อ/ขอแก้ไข → แนบผล → ปิดเรื่อง โดยเก็บประวัติทุกขั้นและไม่ลบเลขทะเบียน

ข้อมูลที่ควรเพิ่ม: owner/assignee UID, routingEvents, dueAt, receivedAt, acknowledgment, completionNote, relatedDocumentIds; แยกข้อมูลต้นฉบับกับบันทึกการดำเนินงาน

ตรวจรับ:

- สร้างไม่มีไฟล์ได้ตามนโยบาย; แนบไฟล์แล้วเปิดได้จากอีกเครื่อง
- แทงให้ผู้ใช้ ก แล้ว reload ต้องยังเป็น ก; ส่งต่อ ข ต้องเห็นประวัติ ก → ข
- ผู้ไม่มีสิทธิ์รับเรื่อง/ปิดเรื่องแทนไม่ได้; ตีกลับต้องมีเหตุผล
- ค้นหา กรอง ส่งออก ได้รายการเดียวกัน; สร้างพร้อมกันสองคนเลขไม่ซ้ำ

## 3. ทะเบียนหนังสือส่ง — /admin/outbound

หลักฐาน: [หน้า outbound](<D:/Faculty of Liberal Arts and Sciences/app/admin/outbound/page.tsx:130>), [updateOutboundDocStatus](<D:/Faculty of Liberal Arts and Sciences/lib/firebaseService.ts:284>)

มีแล้ว: สร้างหนังสือ ออกเลข กรอง ส่งออก แนบไฟล์ฉบับลงนาม เปลี่ยนสถานะ signed/completed/cancelled

ตรวจรับ: ยกเลิกแล้ว reload ยังเห็นเหตุผล; การลงนามต้องมีหลักฐานที่รองรับตามวิธีลงนามที่เลือก; เอกสารร่างข้ามไปส่งแล้วไม่ได้; sentAt/channel/recipient/proof คงอยู่; retry ไม่ออกเลขเพิ่ม

## 4. สร้างบันทึกข้อความ — /admin/memo-generator

หลักฐาน: [หน้า memo](<D:/Faculty of Liberal Arts and Sciences/app/admin/memo-generator/page.tsx:133>), [Word generator](<D:/Faculty of Liberal Arts and Sciences/lib/documentGenerator.ts:22>), [print CSS](<D:/Faculty of Liberal Arts and Sciences/app/globals.css:41>)

มีแล้ว: เชิญวิทยากรเดี่ยว/หลายคน ขอเวลาเรียน เดินทางไปราชการ และเสนอผ่านคณบดี รวมทั้งบันทึกและเปิดร่าง ส่งออก Word และเรียกพิมพ์

ข้อบกพร่อง P1:

- save payload ไม่บันทึก `speakers`; โหลดร่างไม่คืนชนิดแม่แบบและตารางวิทยากร ทำให้เปิดกลับแล้วไม่เหมือนต้นฉบับ
- เปลี่ยนแม่แบบขณะมี `activeMemoId` ไม่เคลียร์ id หากตั้งใจสร้างอีกฉบับแล้วกดบันทึก จะทับร่างที่เปิดอยู่ ต้องแยก “เปลี่ยนแม่แบบฉบับนี้” กับ “สร้างฉบับใหม่” ให้ชัด
- แก้ร่างสำเร็จไม่ได้ปรับรายการ `savedMemos` จึงมีโอกาสโหลดข้อมูลเก่าใน session เดียวกัน
- เนื้อหาตัวอย่าง วันที่กิจกรรม ชื่อบุคคลยัง hardcode; `loadDefaultTemplateContent` ไม่ใช้ย่อหน้ากลางที่รับมา
- ครุฑบน preview แก้ในรอบก่อนแล้ว แต่ `exportMemoToWord` ยังไม่มี ImageRun/ภาพครุฑ
- PDF ใช้ `window.print()`; CSS ซ่อน aside/header/no-print แต่ไม่ได้จำกัดเฉพาะ `printable-document-area` ต้องตรวจ print preview จริงว่าฟอร์ม/ปุ่มไม่ปนเอกสาร และจัดหน้าหลายหน้าได้
- ยังไม่เห็นวงจรส่งตรวจ/ฉบับอนุมัติที่ผูกเป็นหนังสือส่งเดียวกัน

Flow ที่เสนอ: เลือกแม่แบบและรุ่น → เติมข้อมูลจริง → ตรวจช่องบังคับ/แสดงตัวอย่าง → บันทึกร่างครบทุกฟิลด์ → ส่งตรวจ/คืนแก้ → ยืนยันฉบับ → สร้างรายการหนังสือส่งที่อ้าง memoId → แนบผลลงนาม/ส่งออก โดยไม่ออกเลขซ้ำ

ตรวจรับ: ร่างวิทยากร 3 คนปิดเปิดแล้วยังครบและแม่แบบเดิม; สร้างฉบับใหม่ไม่ทับเก่า; เปิดร่างหลังแก้ได้ข้อมูลล่าสุด; Word/PDF มีข้อมูลตรงกัน ครุฑไม่บิด รูปแบบ A4 และตารางหลายหน้าตรวจด้วยการเปิดไฟล์จริง

## 5. แบบตอบรับวิทยากร/สถานที่ — /admin/responses

มีแล้ว: แยกแม่แบบ ตอบรับ/ปฏิเสธ เก็บผู้ติดต่อและรายชื่อกิจกรรม บันทึกประวัติและส่งออก Word

ข้อบกพร่อง P1:

- ทุก save เป็น `createResponse` ใหม่ ไม่มี update รายการเดิมหรือ idempotency; กดบันทึกซ้ำอาจมีเลขเดียวกันหลายรายการ

- สถานะ confirmed ทันทีไม่ได้แยกเจ้าหน้าที่กรอกแทน/ได้รับหลักฐานจริง/ตรวจแล้ว

- จำนวนผู้ร่วมใช้ความยาว array รวมแถวว่าง; การ validate ก่อนบันทึกยังไม่ครบ และมี undefined ใน payload

Flow ที่เสนอ: เลือกหนังสือเชิญ → ลงข้อมูลตอบรับหรือบันทึกแทนพร้อมที่มา → เลือกยินดี/ไม่สามารถ/เงื่อนไข → แนบต้นฉบับตามนโยบาย → ตรวจข้อมูล → ยืนยัน → อัปเดตผู้เข้าร่วม/สถานที่ในงานที่เกี่ยวข้อง; การแก้คำตอบต้องมี revision

ตรวจรับ: save ซ้ำไม่เพิ่มรายการ; ปฏิเสธไม่เติมเหตุผลเอง; รายชื่อว่างไม่ถูกนับ; เปิดจากหนังสือเชิญเห็นคำตอบตรงฉบับ; แก้คำตอบยังดูประวัติและหลักฐานเดิมได้

## 6. เช็คลิสต์ตรวจเอกสาร — /admin/checklists

หลักฐาน: [นิยามรายการและการบันทึก](<D:/Faculty of Liberal Arts and Sciences/app/admin/checklists/page.tsx:35>), [createChecklist](<D:/Faculty of Liberal Arts and Sciences/lib/firebaseService.ts:575>), [ทะเบียนต้นฉบับ](<D:/Faculty of Liberal Arts and Sciences/docs/audit/03-source-inventory.md>)

มีแล้ว: เริ่มรายการแบบยังไม่ตรวจ เลือก yes/no/na ใส่หมายเหตุ บันทึกประวัติ และแสดงใบตรวจ

P0: service เขียน collection `admin_checklists` แต่ไม่พบ match รองรับใน firestore.rules ที่อยู่ใน repo หาก deploy rules ชุดนี้ การอ่าน/เขียนจะถูกปฏิเสธ และ getter ยังซ่อนข้อผิดพลาดด้วย local fallback

P1 ด้านเนื้อหาและการรับรอง:

| ชุดเอกสาร | ต้นฉบับในโปรเจกต์ | หน้าเว็บปัจจุบัน | งานที่ต้องทำ |
|---|---|---|---|
| ยืมเงินโครงการ | 12 ข้อ | 12 ข้อ | จำนวนเท่ากันแต่เนื้อหา/ลำดับไม่ตรง เช่นต้นฉบับเริ่มบันทึกขอยืม ส่วนเว็บเริ่มสัญญา ต้องเทียบรายข้อ |
| เบิกเงินโครงการ | 14 ข้อ | 12 ข้อ | คืนรายการและเงื่อนไขตามต้นฉบับ ไม่ลด/แต่งข้อเอง |
| ค่าสอน | 10 ข้อ | รวมค่าสอน/นิเทศ 8 ข้อ | แยกแม่แบบค่าสอน |
| ค่านิเทศ | 8 ข้อ | รวมค่าสอน/นิเทศ 8 ข้อ | แยกแม่แบบนิเทศโดยใช้รายการเฉพาะ |
| เดินทาง | มีแม่แบบต่างกรณี 7/10/9 ข้อ | แบบรวม 8 ข้อ | เลือกตามกรณีและผูกแหล่งอ้างอิงแต่ละแบบ |

ใช้เอกสารในโฟลเดอร์ `5-ใบรายการเรียงลำดับเอกสาร` และ `7-อนุมัติจ่ายเงิน` เป็นฐานการเทียบ รายงานนี้ไม่รับรองว่าเอกสารทุกฉบับเป็นนโยบายล่าสุดของหน่วยงาน ต้องให้เจ้าของงานระบุฉบับใช้จริงก่อนล็อกรุ่นแม่แบบ อย่าเปลี่ยนข้อกำหนด/อัตราภาษีจากการคาดเดา

- `isComplete` ยอมให้ข้อ required ตอบ na แล้วถือว่าครบโดยไม่ตรวจเงื่อนไขและเหตุผล
- เปลี่ยนเป็น verified จากความครบอัตโนมัติ ไม่แยกผู้ยื่นกับผู้ตรวจ; ชื่อผู้ตรวจเริ่มต้นเป็นข้อความตัวอย่าง
- ทุก save สร้างใหม่ ไม่ใช่รอบแก้ไขของชุดเดิม ยังขาดคืนแก้/ส่งใหม่/รับคืนพร้อมกำหนดเวลา
- ไม่มีหลักฐานรายข้อและ template version ผูกกับ submission

Flow ที่เสนอ: เลือกประเภท/กรณี → สร้างชุดเอกสารที่ผูกโครงการ/หนังสือ → แนบหรืออ้างหลักฐานรายข้อ → ผู้ยื่นตรวจตนเอง → เจ้าหน้าที่ตรวจ → คืนแก้พร้อมรายการขาด → ส่งใหม่ → เจ้าหน้าที่รับรอง → ส่งฝ่ายการเงินพร้อมสถานะและลิงก์หลักฐาน

ตรวจรับ: ทวนกับต้นฉบับรายข้อ; N/A ใช้ได้เฉพาะเงื่อนไขที่ตรงและมีเหตุผล; ผู้ยื่นรับรองเองไม่ได้; เปลี่ยนแม่แบบใหม่ไม่แก้ประวัติเก่า; คืนแก้สองรอบยังตามได้; บันทึกจริงผ่าน rules และอีกบัญชีเปิดได้

## 8. ทะเบียนคำสั่ง/ประกาศคณะ — /admin/orders

หลักฐาน: [หน้า orders](<D:/Faculty of Liberal Arts and Sciences/app/admin/orders/page.tsx:121>), [createOrder](<D:/Faculty of Liberal Arts and Sciences/lib/firebaseService.ts:450>)

Flow ที่เสนอ: เลือกลงทะเบียนฉบับที่ลงนามแล้วหรือสร้างร่าง → ตรวจเลข/ปี/ผู้ลงนาม/สมาชิก → ยืนยันและเผยแพร่ตามสิทธิ์ → แก้ไขด้วยฉบับใหม่ที่เชื่อมฉบับเดิม → เพิกถอนพร้อมเหตุผลและเอกสารอ้างอิง

ตรวจรับ: พร้อมกันสองคนเลขไม่ซ้ำ; บันทึกร่างไม่กลายเป็น active; เปิดไฟล์และรายชื่อกรรมการจากอีกเครื่องได้; เพิกถอนยังดูฉบับเดิม/เหตุผล/ฉบับแทนที่ได้; คนไม่มีสิทธิ์เปลี่ยนสถานะไม่ได้

- resource เป็นรายการคงที่; ต้องใช้ resourceId และสถานะพร้อมใช้/ซ่อม/ปิดบริการ ไม่ใช้ชื่อเป็น key
- ยังไม่ตรวจคนขับซ้อนงาน/ความจุ/สิทธิ์การใช้รถครบ และมีค่าเริ่มต้นคนขับเป็นชื่อเฉพาะ
- ตัวกรองรถพิจารณาชื่อมีคำว่า “รถ” แทนชนิดทรัพยากร

Flow ที่เสนอ: เลือกทรัพยากร/ช่วงเวลา → ตรวจว่าง → ส่งคำขอ pending → ผู้ดูแลตรวจสิทธิ์/ความจุ/หนังสือเดินทาง/คนขับ → อนุมัติพร้อมจองช่วงเวลาที่กันชนจริง → แจ้งผล → รับใช้/คืนหรือเสร็จสิ้น → ยกเลิกพร้อมเหตุผลและคืนช่วงเวลา

ตรวจรับ: เปิดสอง session จองช่วงเดียวกันต้องสำเร็จได้เพียงหนึ่งการอนุมัติ; แก้เวลาต้องตรวจ conflict ใหม่; คนขับคนเดียวสองรถเวลาเดียวกันไม่ได้; รถซ่อมจองไม่ได้; ยกเลิกแล้วช่วงเวลากลับมาจองได้; pending ไม่แสดงเป็นอนุมัติแล้ว

## ลำดับส่งงานให้ AI ตัวถัดไป

1. แก้ ADM-00A ถึง 00D ที่จำเป็นต่อธุรการก่อน พร้อม Emulator tests; ยังไม่ขยายไปพัฒนาโมดุลอื่น
2. ทำ **ทะเบียนหนังสือรับ** ให้จบวงจรและผ่านตรวจรับก่อน แล้วให้ผู้ใช้ทดสอบ
3. ทะเบียนหนังสือส่ง → แม่แบบกลาง → บันทึกข้อความ → แบบตอบรับ
4. เช็คลิสต์โดยเทียบเอกสารจริง → คำสั่ง/ประกาศ → ห้อง/รถ
5. ปรับแดชบอร์ดให้สะท้อน workflow จริง แล้วทดสอบเชื่อมตั้งแต่รับเรื่องถึงปิดงาน

### ข้อความพร้อมคัดลอกให้ AI

> อ่าน `docs/audit/2026-10-04-admin-readiness.md` และโค้ดล่าสุดก่อนแก้ ทำเฉพาะงานธุรการ เริ่มฐานร่วม ADM-00A–00D และทะเบียนหนังสือรับ อย่าย้อนเขียนระบบใหม่ทั้งหมด อย่าใช้ mock/localStorage กลบ error ใน production รักษาข้อมูลและการแก้ไขที่มีอยู่ ออกแบบสิทธิ์/สถานะ/เลขทะเบียน/ไฟล์/audit ให้สอดคล้องกันทั้ง UI, service และ rules ทำ flow รับหนังสือ → ลงทะเบียน → สั่งการ/มอบหมาย → รับทราบ → ดำเนินการ → ปิดเรื่องให้ครบ พร้อมประวัติ เกณฑ์ตรวจรับ และทดสอบหลายบัญชี/พร้อมกัน ใช้ Emulator หรือฐานทดสอบ ห้าม seed/delete ข้อมูลจริง เมื่อจบรายงานไฟล์ที่แก้ ผลทดสอบ และข้อจำกัด แล้วหยุดที่หัวข้อนี้เพื่อให้ตรวจรับก่อนทำหัวข้อถัดไป ไม่ deploy โดยอัตโนมัติ

## หลักฐานการตรวจและข้อจำกัด

- ตรวจหน้า admin ทั้ง 9 route, handlers, service ที่เรียก, numbering, template config, Word/print path, Firestore rules และ firebase.json
- เทียบข้อความ checklist กับเอกสารที่สกัดไว้จากต้นฉบับในโปรเจกต์; ไม่ได้ตรวจรับนโยบายปัจจุบันแทนหน่วยงาน และไม่ได้อ่าน PDF สแกนทั้งหมดใหม่
- รอบนี้เปลี่ยนเฉพาะชื่อหัวข้อและเอกสารรายงาน; `npx tsc --noEmit --incremental false` ผ่าน
- ยังไม่ได้ทดสอบ browser UAT, Firestore/Storage ที่ deploy, Emulator rules, concurrent sessions หรือเปิดไฟล์ Word/PDF ที่สร้างใหม่ ข้อเหล่านี้เป็นงานตรวจรับที่ต้องทำ ไม่ใช่ผลผ่านแล้ว
- ไม่ deploy และไม่เขียนข้อมูล production
