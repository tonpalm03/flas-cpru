# ข้อกำหนดบัญชีผู้ใช้ รูปประจำตัว และลงเวลาทำงาน

ข้อเสนอสำหรับพัฒนาต่อ วันที่ 29 กันยายน 2569 เป็น flow ที่เสนอ ไม่ใช่ฟังก์ชันที่ยืนยันว่าระบบปัจจุบันทำแล้ว

## 1. เป้าหมายและฐานที่มีอยู่

ให้ผู้ดูแลบริหารบัญชีและข้อมูลทุกโมดุลได้ บุคลากรแก้โปรไฟล์และรูปของตนเองได้ ลงเวลาเข้า/ออก ดูประวัติ ขอแก้ไขเวลา และให้หัวหน้า/HR ตรวจรับรองข้อมูลประจำเดือนได้

จากโค้ดล่าสุดที่ตรวจในรอบนี้:

- UserProfile มี role, status, permissions และ avatarUrl แล้ว มีบทบาทเจ้าหน้าที่แยกฝ่าย
- RoleContext ใช้ Firebase Auth listener แล้ว มีบริการ audit และข้อมูล HR ให้ต่อยอด
- ยังไม่พบ route เฉพาะจัดการผู้ใช้ โปรไฟล์ หรือ attendance ใน app ที่ตรวจ
- registerWithEmail ยังรับ role จาก client และสร้าง status เป็น active; rules สร้าง users อนุญาตเจ้าของ UID แต่ยังไม่บังคับ role/status เริ่มต้น จึงต้องแก้ก่อนเพิ่มเมนูผู้ดูแล
- การตรวจ suspended มีใน auth service แต่ data rules หลาย collection ยังตรวจเพียง authenticated ต้องบังคับ account status ที่ data layer ด้วย การซ่อนเมนูหรือ logout อย่างเดียวไม่เพียงพอ
- next.config.mjs ยังเป็น static export งาน Admin SDK เช่นสร้าง/ปิดบัญชี เปลี่ยนสิทธิ และงานลงเวลาที่ต้องตรวจ server ต้องมี trusted backend แยก หรือปรับ hosting ให้รองรับ server ก่อนใช้ API routes
- รายงานนี้ไม่ได้ตรวจซ้ำทั้งระบบและไม่ได้ยืนยันการ deploy ของงานจาก AI ตัวก่อน

## 3. บทบาทและคำว่า “แก้ทุกอย่างได้”

แยกตำแหน่งบุคลากร สิทธิระบบ และอำนาจอนุมัติออกจากกัน คนเดียวอาจรับหลายหน้าที่ ต้องรองรับหลายบทบาทหรือ permission grants ที่มีขอบเขตหน่วยงานและวันมีผล

| บทบาท | ทำอะไรได้ |
|---|---|
| Super Admin | จัดการบัญชี บทบาท การตั้งค่า และแก้ข้อมูลทุกโมดุลตามกระบวนการแก้ไขที่ตรวจสอบได้ |
| Admin โมดุล | แก้ข้อมูลของโมดุลที่ได้รับมอบหมาย ไม่ได้แต่งตั้ง Super Admin เอง |
| HR | ดูแลทะเบียนบุคลากร ตารางงาน วันหยุด ตรวจเวลา สิทธิลา และปิดงวดตามขอบเขต |
| หัวหน้า/ผู้อนุมัติ | ตรวจและอนุมัติรายการของบุคลากรที่อยู่ในสายบังคับบัญชาหรือได้รับมอบหมาย |
| บุคลากร | ดู/แก้ข้อมูลทั่วไปและรูปของตน ลงเวลา ดูประวัติตน และยื่นคำขอ |
| ผู้ตรวจสอบ | อ่านรายงานและประวัติที่ได้รับมอบหมาย ไม่มีสิทธิแก้ไข |

หลักการใช้งาน:

1. ข้อมูลทั่วไป เช่นชื่อเรียก รูป เบอร์ติดต่อ ให้เจ้าของแก้ได้
2. รหัสบุคลากร ชื่อทางการ หน่วยงาน ตำแหน่ง หัวหน้า ตารางงาน และวันเริ่มงาน ให้ HR/ผู้ดูแลแก้พร้อมวันมีผล
3. role, permission, account status ให้ผู้มีสิทธิจัดการบัญชีแก้ผ่าน backend เท่านั้น
4. งานที่อนุมัติ/ลงนามแล้ว ให้สร้างฉบับแก้ไขหรือรายการปรับปรุง ไม่เขียนทับหลักฐานเดิม
5. เวลาเข้างานดิบห้ามแก้ทับ แม้ Super Admin ให้สร้าง correction พร้อมเหตุผล ผู้กระทำ และเวลา
6. รายการเงินที่ลงบัญชีแล้วใช้ reversal/adjustment ตามโมดุลเดิม ห้ามสิทธิใหม่เปิดทางลบ transaction ที่ตรวจสอบไม่ได้
7. รหัสผ่านเดิมต้องเปิดดูไม่ได้ ใช้ reset flow ไม่ส่งรหัสผ่านให้ผู้ดูแล
8. ป้องกันระงับ/ลดสิทธิ Super Admin คนสุดท้ายผ่านทุกช่องทาง และมี recovery procedure ขององค์กร
9. ห้ามผู้ขออนุมัติคำขอแก้เวลาของตัวเอง ให้ส่งผู้อนุมัติสำรอง กรณีฉุกเฉินต้องเป็น exception ที่มีผู้ตรวจทานแยก

Permission ควรเป็น action+scope เช่น users.manage, roles.assign, employees.update.department,
attendance.read.own, attendance.read.department, attendance.correct.request,
attendance.correct.approve, attendance.period.close, attendance.period.reopen ไม่ตรวจแค่ชื่อ role บนหน้าเว็บ

## 4. Flow A — เพิ่มและเปิดใช้บัญชี

แนวทางหลักที่เสนอ: HR/ผู้ดูแลสร้างทะเบียนบุคลากรและส่งคำเชิญ เพื่อผูกกับบุคลากรจริงได้แน่นอน

```text
ผู้ดูแลเพิ่มบุคลากร
→ ตรวจรหัสบุคลากร/บัญชีซ้ำ
→ กำหนดหน่วยงาน ตำแหน่ง หัวหน้า ตารางงาน และวันเริ่มงาน
→ สร้างคำเชิญอายุจำกัดแบบใช้ครั้งเดียว
→ บุคลากรยืนยันช่องทางติดต่อและตั้งรหัสผ่าน
→ ผูก Firebase UID กับ employeeId
→ ผู้มีสิทธิอนุมัติและมอบบทบาท
→ บัญชี active
→ บุคลากรเติมโปรไฟล์/รูป
→ เริ่มใช้งานตามสิทธิและวันที่เริ่มงาน
```

หากต้องเปิดสมัครเอง: สร้าง pending_approval ด้วยสิทธิขั้นต่ำ ห้ามเลือกสิทธิจริงเอง อนุญาตระบุบทบาทที่ขอได้เป็น requestedRole เท่านั้น ต้องรอผู้ดูแลตรวจและผูกกับ employeeId ก่อนใช้งานข้อมูลคณะ

แยกสถานะ invitation ออกจาก account:

- invitation: pending / accepted / expired / revoked
- account: pending_approval / active / suspended / archived
- employment: สถานะทำงาน ลาออก เกษียณ ฯลฯ ตามทะเบียน HR

ผู้ใช้อาจเป็นบัญชีบริการหรือผู้ตรวจสอบที่ไม่ต้องลงเวลา อย่าบังคับสร้าง employee สำหรับทุกบัญชี กำหนด attendanceEligible จากหน้าที่และวันมีผล

ระบบต้องรับมือ Auth account ถูกสร้างแล้ว profile ล้มเหลวอย่างกู้คืนได้ ไม่สร้าง fallback active ขึ้นมาเอง

## 5. Flow B — แก้ไข ระงับ และปิดบัญชี

```text
ผู้ดูแลค้นหาผู้ใช้ → เปิดรายละเอียด
→ เลือกแก้โปรไฟล์ / หน่วยงาน / บทบาท / ส่ง reset / ระงับ
→ backend ตรวจสิทธิและข้อจำกัด
→ กรอกเหตุผลสำหรับการเปลี่ยนสิทธิหรือสถานะ
→ บันทึกพร้อม audit ก่อน–หลัง
→ ปรับสิทธิของ session ที่เกี่ยวข้อง
→ แจ้งผู้ได้รับผลกระทบ
```

เมื่อระงับ/สิ้นสุดงาน: ปฏิเสธการเข้าถึงข้อมูลและลงเวลาใหม่ที่ backend/rules, ปิดบัญชี Auth หรือเพิกถอน session ตามเหตุการณ์, จัดการงานค้างและผู้อนุมัติแทน, เก็บประวัติ employeeId/ผู้ลงนามเดิม ไม่ลบชื่อออกจากเอกสารย้อนหลัง

เมื่อเปลี่ยนอีเมลที่ใช้ login ต้องใช้ Auth change flow พร้อมยืนยันตัวตน/อีเมลและ sync profile ไม่แก้ Firestore email เพียงช่องเดียว ส่วนการเปลี่ยนหน่วยงาน/หัวหน้าต้องมี effective date เพื่อรักษาประวัติสายอนุมัติ

## 6. Flow C — รูปประจำตัว

```text
โปรไฟล์ของฉัน → เลือกรูป → ครอบภาพ/หมุน/ดูตัวอย่าง
→ อัปโหลด → ตรวจสิทธิ ชนิดจริง ขนาด และประมวลผลรูป
→ บันทึก path ของรูปใหม่ → แสดงใน Navbar/ทะเบียนบุคลากร
→ ยกเลิกการอ้างอิงรูปเก่าและจัดการตามนโยบายเก็บไฟล์
```

ค่าเริ่มต้นที่เสนอ: JPG/PNG/WebP ไม่เกิน 5 MB, thumbnail 256×256 และรูปแสดงผล 512×512; ปรับได้ตามข้อจำกัดงานจริง ตรวจขนาดพิกเซลและเนื้อหาไฟล์ ไม่เชื่อเฉพาะ extension/MIME จาก client ลบ EXIF เมื่อประมวลผลและใช้ชื่อไฟล์ที่ไม่เปิดเผยข้อมูลส่วนตัว

เก็บ Storage path+version+updatedAt ไม่เก็บ base64 ใน users document อัปโหลดล้มเหลวต้องคงรูปเก่า เปลี่ยนรูปแล้วจัดการ cache ให้แสดงรูปใหม่ทุกหน้า ปุ่มลบรูปกลับไปใช้ตัวอักษรย่อ

รูปประจำตัวมีไว้แสดงตัวตน ไม่ถือเป็นหลักฐานเช็กอินหรือระบบจดจำใบหน้า ไม่เพิ่ม face recognition/selfie ทุกครั้งโดยไม่มีข้อกำหนดจากเจ้าของระบบ

แยกข้อมูล directory ที่บุคลากรทั่วไปเห็นได้ออกจากข้อมูลส่วนตัว ไฟล์รูป/ข้อมูล HR ต้องใช้สิทธิอ่านให้ตรงวัตถุประสงค์ ไม่เปิดทั้งทะเบียนส่วนบุคคลเพื่อแสดง avatar

## 7. Flow D — ตั้งค่าลงเวลาก่อนเปิดใช้

HR กำหนดและเผยแพร่ policy ที่มี version และวันเริ่มใช้:

- timezone Asia/Bangkok; เก็บ instant ฝั่ง server เป็น UTC และผูกวันทำงานตามตารางงาน
- วันทำงาน วันหยุด เวลามา/กลับ ช่วงพัก เวลาผ่อนผัน และรูปแบบกะ
- บุคลากรที่ต้องลงเวลาและการมอบหมายตารางงานแต่ละช่วง
- ทำงานในคณะ/นอกสถานที่/ไปราชการ/รูปแบบงานอื่นที่หน่วยงานอนุญาต
- ผู้อนุมัติคำขอแก้ไข กำหนดส่งคำขอ วันปิดงวด และผู้เปิดงวดใหม่
- รูปแบบยืนยันสถานที่และแนวทางกรณีอุปกรณ์/เครือข่ายใช้ไม่ได้

อย่าคำนวณเวลาสาย/วันขาดจากตัวอย่าง 08:30–16:30 จนกว่าจะมีตารางงานจริงของบุคคลนั้น ค่าอัตราเวลา/กะ/วันหยุดต้องมีรุ่นเพื่อรักษารายงานย้อนหลัง

ทางเลือกการยืนยันสถานที่ให้เจ้าของระบบเลือกก่อนเปิดใช้:

| วิธี | การใช้งาน | ข้อจำกัดที่ต้องออกแบบ |
|---|---|---|
| กดเข้า–ออกหลัง login | เริ่มใช้งานง่าย เหมาะกับระบบที่ใช้ความรับผิดชอบและการตรวจย้อนหลัง | เป็นการรายงานตนเอง ไม่ยืนยันว่าอยู่ในคณะ |
| GPS ตามสถานที่อนุญาต | ลงเวลาผ่านมือถือ ตรวจพิกัดและความแม่นยำ | GPS คลาดเคลื่อน/ปฏิเสธ permission ได้ และไม่ใช่หลักฐานป้องกันปลอมที่สมบูรณ์ ต้องมี exception flow |
| QR เปลี่ยนตามช่วงเวลาที่จุดลงเวลา | เหมาะมีจุดลงเวลาประจำ | QR ต้องหมดอายุ ตรวจ replay ที่ backend; การส่งภาพต่อยังเป็นข้อจำกัด ห้ามอ้างว่าป้องกันลงเวลาแทนได้ทั้งหมด |
| เครื่องลงเวลา/บัตรที่มีอยู่ | เหมาะต้องการใช้เครื่องเดิมเป็นต้นทาง | ต้องมี mapping employeeId, import idempotent และความชัดเจนของเวลาเครื่อง |

ข้อเสนอรอบแรก: ทำแกนลงเวลา+ประวัติ+คำขอแก้ไข+อนุมัติ+รายงานให้ครบ และเลือกวิธียืนยันสถานที่หนึ่งแบบตามสภาพการทำงานจริง ไม่เปิด GPS/ถ่ายรูปเป็นค่าเริ่มต้นโดยยังไม่กำหนดนโยบาย

หากใช้ตำแหน่ง เก็บเฉพาะขณะกดลงเวลา ไม่ติดตามต่อเนื่อง แสดงวัตถุประสงค์ก่อนขอ permission กำหนดผู้เห็นและระยะเวลาเก็บข้อมูล

## 8. Flow E — ลงเวลาเข้า–ออก

```text
บุคลากรเปิดหน้าลงเวลา
→ แสดงวันนี้ ตารางงาน สถานที่ สถานะและเวลาที่บันทึกล่าสุด
→ กดเข้างาน
→ backend ตรวจ account active, employee, วันเริ่ม/สิ้นสุดงาน,
   ตารางงาน, session ค้าง, หลักฐานสถานที่ถ้ามี และ requestId
→ บันทึก raw event ด้วยเวลา server แบบ atomic
→ แสดงสำเร็จพร้อมเวลา/เลขอ้างอิงจาก server
→ เมื่อเสร็จงานกดออกงาน
→ ตรวจ session ที่ต้องปิดและ policy
→ บันทึก checkout event
→ คำนวณสรุปตาม schedule/policy รุ่นที่ใช้
```

ต้องรองรับ:

1. กดซ้ำ/สองเครื่อง/request retry: ใช้ idempotency key และ atomic operation ไม่เกิดสอง session ทับกัน
2. เปลี่ยนเวลาบนมือถือ: เวลาราชการของรายการต้องใช้ server ไม่ใช้ Date.now จาก client เป็นหลักฐาน
3. ข้ามเที่ยงคืน: ผูก checkout กับ work session/shift ที่เปิดอยู่ ไม่สร้างเป็นกะใหม่เพราะวันที่ปฏิทินเปลี่ยน
4. ลืมออกงาน: แสดง incomplete/needs_review ไม่ปิดเวลาสมมติให้เอง
5. ออกแล้วต้องกลับมาทำงาน: รองรับหลาย session ตาม policy หรือส่งคำขอ ห้ามเกิดกรณีปุ่มค้างโดยแก้ไม่ได้
6. กดออกโดยไม่เข้า: แสดงเหตุผลและทางยื่นขอแก้ไข ไม่สร้างเวลาเข้าย้อนหลังเอง
7. เครือข่ายล้มเหลว: แสดงยังไม่ยืนยัน ห้ามแสดงลงเวลาสำเร็จจนได้ acknowledgment; ถ้า request timeout ให้ค้นผลด้วย requestId ก่อน retry
8. ไม่เปิด offline auto-accept ในรอบแรก ให้ยื่นคำขอพร้อมเวลาที่อ้างและเหตุผล ถ้าต้องทำ offline ภายหลังต้องแยก claimed time กับ server received time และผ่านการตรวจ
9. GPS/QR ไม่ผ่าน: บอกเหตุผลที่แก้ได้ และเปิดเส้นทางขอรับรองกรณีพิเศษ ไม่บล็อกจน HR แก้ไม่ได้
10. เวลาปัจจุบันไม่มีตารางงาน: แจ้ง HR จัดตาราง ไม่ตีว่า absent/late โดยเดากติกา

แยกสถานะเป็นมิติต่าง ๆ ไม่ใช้ enum เดียวที่แทนทุกอย่าง:

- session: open / closed / incomplete
- เวลาเทียบตาราง: on_time / late / early_leave / missing_punch
- การปฏิบัติงานตาม HR: work / holiday / approved_leave / official_duty / outside_work / unexcused_absence
- การรับรอง: unreviewed / correction_pending / approved / locked

เช่น วันหนึ่งอาจมาสายและออกก่อนพร้อมกัน หรือมีใบลาครึ่งวันและทำงานอีกครึ่งวัน

## 9. Flow F — ขอแก้ไขและผู้ดูแลแก้ย้อนหลัง

```text
บุคลากรเลือกวัน/รายการ → ระบุเวลาใหม่ เหตุผล และหลักฐานถ้ามี
→ ระบบแสดงค่าเดิมเทียบค่าที่ขอ → ส่งผู้อนุมัติตามสายงาน
→ หัวหน้าหรือผู้มีสิทธิ ตรวจ / ส่งกลับ / อนุมัติ / ปฏิเสธ
→ backend ตรวจสิทธิ สถานะงวด และ version ของข้อมูลเดิม
→ เมื่ออนุมัติ สร้าง adjustment ไม่เขียนทับ raw event
→ คำนวณ daily summary ใหม่ → แจ้งผลผู้ยื่น
```

ผู้ดูแลแก้แทนบุคลากรใช้ flow เดียวกัน แต่ระบุ initiatedBy=admin และ onBehalfOf=employee ไม่ปลอมตัวเป็นผู้ใช้ ต้องมี reason และบอกผู้ได้รับผลกระทบ

คำขอซ้อนกันต้องตรวจ version; อนุมัติคำขอเก่าหลังมีการแก้ใหม่แล้วไม่ได้โดยไม่ทวน กำหนดผู้อนุมัติสำรองเมื่อหัวหน้าลา/ไม่มีหัวหน้า ห้ามคิวงานหาย

หากงวดล็อกแล้ว: ยื่น reopen request พร้อมเหตุผล → ผู้มีอำนาจเปิดงวด → บันทึก correction → ตรวจสรุป → ปิดงวดใหม่ เก็บ report version เก่าและใหม่

## 10. Flow G — เชื่อมใบลา ไปราชการ และปิดงวด

```text
raw attendance + approved corrections + work schedules + holidays
+ approved leave + approved official duty/outside work
→ daily summaries
→ HR ตรวจรายการขาด/ผิดปกติ
→ ส่งหัวหน้ารับรองตามที่หน่วยงานกำหนด
→ แก้ไขข้อขัดแย้ง
→ HR ปิดงวด
→ export รายงานพร้อม version และวันปิดงวด
```

ใบลายัง pending ไม่ถือเป็นลาที่อนุมัติแล้ว และ “ไม่มีเวลาเข้า” ต้องเป็นรอตรวจจนพ้นเวลาตัดรอบ/ตรวจลา/ตรวจไปราชการ จึงจะสรุปเป็นขาดงานตามกติกา ห้ามสร้าง punch ปลอมเพื่อให้วันลาแสดงครบ

รองรับลาเป็นช่วงเวลา วันหยุดพิเศษ และกะคร่อมวัน หากเวลาเข้า–ออกขัดกับใบลาให้เป็น conflict ที่ตรวจได้ ไม่เลือกทับกันเงียบ ๆ เวลาหลังเลิกงานเป็นเวลาที่บันทึก ไม่ถือเป็น OT อนุมัติอัตโนมัติ

รายงานขั้นต่ำ: รายวันใน scope, รายบุคคลรายเดือน, มาสาย/ออกก่อน/ขาดการลงเวลา, ลา/ไปราชการ, คำขอแก้ไข, ประวัติผู้แก้, งวดที่รับรองแล้ว

รายงาน Excel ต้องระบุวันตามเวลาไทย จำนวนวัน/นาที สูตรรวมที่ตรง policy และไม่แสดงรายละเอียดตำแหน่งหรือข้อมูลส่วนตัวเกินสิทธิ การเชื่อมเงินเดือน/หักเงินเป็นอีกขอบเขตหนึ่ง ไม่ทำอัตโนมัติในรอบนี้

## 11. ข้อมูลหลักที่ต้องมี

| Entity ที่เสนอ | ฟิลด์สำคัญ |
|---|---|
| users | uid, employeeId ถ้ามี, accountStatus, roles/grants, avatarPath, createdAt/updatedAt |
| employees | employeeId, officialName, departmentId, position, supervisorAssignments, employmentDates, attendanceEligible |
| roleAssignments | uid, roleId, scope, validFrom/validTo, grantedBy |
| invitations | tokenHash, intendedAccount, expiresAt, usedAt, status |
| workPolicies | version, timezone, grace/break rules, correction limits, effective dates |
| workSchedules/assignments | employeeId/groupId, workDate/shift, start/end, locationId, policyVersion |
| holidays | calendarId, date, description, applicableGroups |
| attendanceEvents | eventId, employeeId, type, serverAt, requestId, sessionId, evidence, source |
| workSessions | sessionId, employeeId, shiftId/workDate, checkInEventId, checkOutEventId, version |
| attendanceCorrections | beforeVersion, proposedValues, reason, evidence, requestedBy, reviewedBy, status, timestamps |
| attendanceDailySummaries | employeeId, workDate, scheduleVersion, leave/duty refs, actualMinutes, late/early minutes, exceptions, version |
| attendancePeriods | period, scope, status, closedBy/At, reopenedBy/reason, reportVersion |
| auditEvents | authenticatedActor, action, target, changedFields, reason, serverAt, requestId |

ชื่อ collection ให้ใช้ naming convention ปัจจุบันของโปรเจกต์ ไม่ต้องสร้าง audit ใหม่หากต่อยอดของเดิมได้ แต่ actor/time ของ privileged audit ต้องมาจาก backend ไม่เชื่อค่าที่ client ส่งเอง

การมอบสิทธิ/ระงับบัญชี/ปรับเวลาและ audit ที่จำเป็นต้องสำเร็จอย่างสอดคล้อง หาก audit สำคัญล้มเหลวต้องไม่รายงานว่า operation เสร็จครบโดยไม่มีประวัติ

## 12. ลำดับพัฒนา

1. แก้ account creation/rules และ permission model; เพิ่ม employeeId ที่ไม่เปลี่ยนตามชื่อ/อีเมล
2. จัดการผู้ใช้ คำเชิญ เปิด/ระงับบัญชี reset และโปรไฟล์/รูป
3. ทะเบียนบุคลากร ตารางงาน วันหยุด policy และสายอนุมัติ
4. raw check-in/out + sessions + server validation + ประวัติของฉัน
5. correction/approval/notification และ audit ที่ backend รับรอง
6. เชื่อมใบลา/ไปราชการ สรุปรายวัน ปิดงวดและ export
7. เลือกเปิดหลักฐานสถานที่ตาม policy และทดสอบหลายผู้ใช้ก่อน production

## 13. เกณฑ์ตรวจรับ

- สมัครใหม่ไม่สามารถส่ง role/status เพื่อเป็น admin หรือ active โดยข้ามผู้อนุมัติได้
- ผู้ใช้เปลี่ยนรูปและเบอร์ของตัวเองได้ แต่เปลี่ยน employeeId/role/status/หน่วยงานไม่ได้
- เปลี่ยนอีเมล login แล้ว Auth และ profile สอดคล้อง บัญชีที่ไม่มี profile ไม่ได้ active อัตโนมัติ
- ระงับบัญชีที่เปิดหน้าค้างอยู่แล้วต้องไม่สามารถเขียนข้อมูล/ลงเวลาใหม่ได้ แม้เรียก data layer โดยตรง
- Admin จัดการผู้ใช้อื่นโดยไม่ทำให้ session ของตนกลายเป็นบัญชีที่สร้างใหม่
- เปลี่ยนรูปสำเร็จทุกหน้าตาม version; ไฟล์เสีย/อัปโหลดล้มเหลวไม่ทำให้รูปเดิมหาย
- ผู้ไม่มีสิทธิอ่านไฟล์ HR/หลักฐานตำแหน่งไม่ได้ รวมถึงเข้าจาก URL โดยตรงตามรูปแบบ storage ที่ใช้
- สองเครื่องลงเวลาเวลาเดียวกันหรือส่ง request ซ้ำไม่สร้าง event/session ซ้ำ
- เปลี่ยนนาฬิกาเครื่องแล้วเวลาที่รับรองยังมาจาก server
- checkout กะข้ามคืนจับคู่ถูกต้อง กะค้างไม่ถูกปิดด้วยเวลาสมมติ
- เครือข่าย timeout แล้วตรวจด้วย requestId ทราบได้ว่าบันทึกสำเร็จหรือไม่
- ใบลารออนุมัติ ใบลาอนุมัติ วันหยุด ลาครึ่งวันและไปราชการให้ผลต่างกันถูกต้อง
- ไม่มีตารางงาน/ไม่มี punch ยังไม่ถูกสรุปเป็นขาดโดยไม่ผ่านกติกาตัดรอบและตรวจข้อยกเว้น
- ขอแก้ไขเวลาไม่เปลี่ยนยอดที่รับรองจนกว่าอนุมัติ ผู้ขออนุมัติตัวเองไม่ได้
- คำขอซ้อนกันและการแก้ข้อมูลพร้อมกันถูกตรวจ version ไม่ทับผลใหม่
- งวดล็อกแก้ตรงไม่ได้ reopen มีเหตุผลและ report version เก่ายังย้อนดูได้
- Super Admin คนสุดท้ายไม่ถูกลดสิทธิ/ระงับจนระบบไม่มีผู้ดูแล
- export รวมวัน/นาทีตรงรายการและ policy ที่ใช้ ไม่ถือเวลาหลังเลิกงานเป็น OT โดยอัตโนมัติ
- ตรวจ UI บนมือถือจริง กรณีปฏิเสธตำแหน่ง อัปโหลดรูป และข้อมูลว่าง/error
- ทดสอบทั้ง allowed/denied ที่ backend และ rules ไม่ใช่เพียงปุ่มหายบน UI

## 14. ข้อสรุปที่เจ้าของระบบต้องเลือกก่อนเปิดใช้

1. ใช้บัญชีเชิญโดยผู้ดูแล หรือเปิดสมัครเองแล้วรออนุมัติ?
2. ใครต้องลงเวลา และใครได้รับยกเว้น? มีหลายกะ/เข้าออกหลายช่วงหรือไม่?
3. เวลา/วันทำการ/เวลาผ่อนผันของแต่ละกลุ่มคืออะไร?
4. ใช้วิธีรายงานตนเอง GPS QR หรือเครื่องเดิม? กรณีทำงานนอกคณะใช้วิธีใด?
5. ใครอนุมัติคำขอแก้เวลา ใครเป็นผู้อนุมัติสำรอง และส่งได้ภายในกี่วัน?
6. ปิดงวดวันไหน ใครเปิดงวดใหม่ได้ และเก็บหลักฐานแต่ละชนิดนานเท่าไร?

พัฒนา schema/UI/flow รองรับคำตอบเหล่านี้ได้ก่อน แต่ไม่ควรเปิดการตัดสินขาด/สายหรือการบังคับพิกัดด้วยค่าที่เดาเอง
