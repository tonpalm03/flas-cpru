# บทบาทผู้ใช้และสิทธิ์จัดการบัญชี

ข้อกำหนดเพิ่มเติมจากผู้ใช้ วันที่ 4 ตุลาคม 2569 ใช้ประกอบรายงานตรวจงานธุรการและข้อกำหนดบัญชีผู้ใช้เดิม

## ข้อกำหนดที่ยืนยันแล้ว

ผู้ใช้ยืนยันครบ 7 บทบาทแล้ว โดยเพิ่มเติม “รองคณบดี” แยกจากคณบดีและผู้บริหาร

| บทบาท | ข้อกำหนดจากผู้ใช้ |
|---|---|
| แอดมิน | แต่งตั้ง/เปลี่ยนบทบาทผู้อื่นได้ แก้ไขรหัสผ่านได้ และลบบัญชีได้ |
| คณบดี | ต้องเป็นบทบาทแยก |
| รองคณบดี | ผู้ใช้ยืนยันเพิ่มเติม ต้องเป็นบทบาทแยก |
| ผู้บริหาร | ต้องแยกจากคณบดี |
| ประธานสาขา | ต้องมีบทบาทเฉพาะ |
| อาจารย์ | ใช้ชื่อแสดงผลนี้ |
| เจ้าหน้าที่ | ใช้เป็นบทบาทหลักของเจ้าหน้าที่ |

สิทธิ์อนุมัติและขอบเขตข้อมูลของบทบาทอื่นนอกจากแอดมินยังไม่ได้รับการระบุจากผู้ใช้ ตารางต่อไปเป็นข้อเสนอเพื่อออกแบบ ไม่ใช่สิทธิ์ที่ยืนยันหรือเปิดใช้งานแล้ว

## ข้อเสนอการแบ่งสิทธิ์

| บทบาท | สิทธิ์ตั้งต้นที่เสนอ |
|---|---|
| แอดมิน | จัดการบัญชี บทบาท การมอบหมายงาน และการตั้งค่าระบบ; แยกสิทธิ์จัดการระบบจากการลงนามแทนผู้มีอำนาจ |
| คณบดี | ดูงานระดับคณะ สั่งการ อนุมัติและลงนามตามกระบวนการที่กำหนด |
| รองคณบดี | ตรวจ พิจารณา และสั่งการในด้านที่รับผิดชอบ; อนุมัติหรือลงนามเมื่อมีการมอบอำนาจที่ระบุขอบเขตและช่วงเวลา |
| ผู้บริหาร | ดูและพิจารณางานเฉพาะด้าน/หน่วยงานที่ได้รับมอบหมาย; มีขอบเขตและระยะเวลาการมอบอำนาจ |
| ประธานสาขา | ดูงานของสาขาตน ตรวจหรือเสนอความเห็นก่อนส่งผู้มีอำนาจอนุมัติ |
| อาจารย์ | จัดการข้อมูลและคำขอของตน รับงานที่ได้รับมอบหมาย ติดตามสถานะ |
| เจ้าหน้าที่ | ทำงานตามโมดุลและหน่วยงานที่แอดมินมอบหมาย ไม่ได้เข้าถึงทุกงานโดยอัตโนมัติ |

แยก **บทบาทหลัก** ออกจาก **สิทธิ์งานรายโมดุล** เช่น เจ้าหน้าที่ + งานธุรการ หรือเจ้าหน้าที่ + การเงิน/พัสดุ ผู้ใช้หนึ่งคนอาจได้รับมอบหมายหลายงาน จึงไม่ควรใช้จำนวนโมดุลเป็นจำนวนบทบาท

ตัวอย่างสิทธิ์งานธุรการ: อ่านทะเบียน, ลงรับ, แก้ข้อมูลต้นเรื่อง, สั่งการ, รับทราบงาน, ลงทะเบียนหนังสือส่ง, ยืนยันหลักฐานลงนาม, ส่งหนังสือ, ยกเลิกเลข, จัดการแม่แบบ แต่ละสิทธิ์มีขอบเขตตนเอง/สาขา/หน่วยงาน/คณะ และตรวจทั้งฐานข้อมูลกับหน้าเว็บ

## Flow จัดการบัญชีสำหรับแอดมิน

1. ค้นหาและเปิดบัญชีเป้าหมาย → ดูตัวตน สถานะ บทบาท และงานที่ค้าง
2. เปลี่ยนบทบาท → เลือกบทบาทหลัก หน่วยงาน และสิทธิ์โมดุล → แสดงรายการเปลี่ยนแปลง → บันทึก → มีผลกับสิทธิ์จริงและบันทึกประวัติ
3. แก้ไขรหัสผ่าน → ใช้การรีเซ็ตผ่านช่องทางยืนยันตัวตน หรือกำหนดรหัสชั่วคราวผ่านบริการฝั่ง server ที่มีสิทธิ์ → ให้เจ้าของบัญชีตั้งรหัสใหม่ → ยกเลิก session เดิมตามนโยบาย ห้ามแสดงรหัสเดิมหรือเก็บรหัสผ่านใน Firestore/audit
4. ลบบัญชี → แสดงบัญชีที่จะลบและงานที่ต้องโอน → ยืนยันรายการนั้น → จัดการบัญชีเข้าสู่ระบบและโปรไฟล์ให้สอดคล้อง → เก็บหลักฐานทะเบียน/เอกสาร/audit ที่เคยทำ ไม่ลบเอกสารราชการพ่วงตามบัญชี
5. ปิดใช้งานชั่วคราวเป็นอีกคำสั่งหนึ่งสำหรับกรณีที่ยังไม่ต้องการลบ และต้องทำให้เข้าใช้ข้อมูลไม่ได้จริง

ป้องกันการลบ/ลดสิทธิ์แอดมินคนสุดท้าย บันทึกผู้กระทำ เวลา บัญชีเป้าหมาย และรายละเอียดการเปลี่ยนแปลงโดยไม่บันทึกรหัสผ่าน การลบบัญชีจริงและการส่งข้อความรีเซ็ตต้องเกิดจากคำสั่งจัดการบัญชีที่ระบุเป้าหมาย ไม่ทำระหว่างการพัฒนาหรือทดสอบ

## ผลต่อโค้ดปัจจุบันและงานส่งต่อ

- `lib/types.ts` ปัจจุบันมี 8 ค่า role: admin, dean, lecturer, staff_finance, staff_procurement, staff_hr, staff_plan, gov_officer ซึ่งไม่ตรงรายการใหม่
- `dean` และตัวเลือกใน `app/settings/users/page.tsx` ยังรวมคณบดี/ผู้บริหาร และคำอธิบาย type รวมรองคณบดี; ยังไม่มีบทบาทรองคณบดี ผู้บริหาร และประธานสาขาแยกตามรายการใหม่
- เสนอให้ mapping staff_* เดิมเป็นเจ้าหน้าที่พร้อมสิทธิ์โมดุลเดิม โดยต้องตรวจข้อมูลจริงและทำ migration ที่ตรวจสอบย้อนหลังได้
- ห้ามแยกผู้ใช้ dean เดิมเป็นคณบดี รองคณบดี หรือผู้บริหารด้วยการเดาชื่อ ต้องมี mapping ที่เจ้าของระบบยืนยันก่อนย้าย
- ตรวจและแก้ UserRole, แบบเชิญ/อนุมัติผู้ใช้, RoleContext, role guards ทุกหน้า, Firestore/Storage rules และ backend ให้ใช้ความหมายเดียวกัน ไม่แก้แค่ป้ายชื่อ
- สิทธิ์จัดการบัญชี/รหัสผ่าน/ลบบัญชีต้องตรวจที่ trusted backend ไม่ฝากสิทธิ์ผู้ดูแลไว้ใน browser

ตรวจรับ: แอดมินมอบหมายและถอนสิทธิ์ได้จริง, ผู้ใช้ทั่วไปยกระดับตนเองไม่ได้, ผู้บริหาร/ประธานสาขาไม่เห็นข้อมูลนอกขอบเขต, สิทธิ์เดิมไม่ค้างหลังถอน, รีเซ็ตรหัสผ่านไม่เปิดเผยรหัสเดิม, ลบบัญชีแล้วเข้าไม่ได้แต่ประวัติงานยังตรวจสอบได้, แอดมินคนสุดท้ายไม่ถูกลบหรือถอดสิทธิ์

สถานะ: ยืนยันชื่อครบ 7 บทบาทและเพิ่มข้อกำหนดเพื่อส่งต่อ AI แล้ว ยังไม่ได้เปลี่ยน role ในระบบหรือย้าย/ลบบัญชีจริง สิทธิ์รายละเอียดของบทบาทอื่นนอกจากแอดมินเป็นข้อเสนอที่ต้องกำหนดตามขอบเขตงานและการมอบอำนาจ
